# 1. 目的与范围

本文档将软件设计文档与技术设计文档转化为可执行的开发计划，包含：

1. 开发阶段划分、每阶段的目标、任务清单与验收标准；
2. 工程规范（代码风格、Git 提交规范、代码审查）；
3. 测试、安全、性能验收计划；
4. 发布与运维流程；
5. 风险清单与应对措施；
6. 人员角色与工作量估算。

> 本方案按"1 名全栈 + 1 名后端（可兼）"的 2 人小团队规模估算，实际排期可随团队规模等比调整。

# 3. 开发环境与工程规范

## 3.1 工具链

| 类别 | 工具 | 说明 |
| --- | --- | --- |
| Rust | rustup + stable | 使用 `rust-toolchain.toml` 锁定版本 |
| IDE | VS Code + rust-analyzer | 后端开发 |
| 前端 | Node.js 20+（仅构建） | esbuild 打包；运行时无 Node 依赖 |
| 数据库工具 | sqlx-cli | 迁移管理 |
| 调试 | curl / HTTPie、浏览器 DevTools | API 与页面调试 |
| 版本管理 | Git | 项目源码仓库托管（GitLab/Gitea/GitHub 均可，属于开发流程工具，与产品 GitLab 联动功能无关） |
| 容器 | Docker（可选） | 本地联调与发布 |
| 测试 | cargo test、Playwright | 自动化测试 |

## 3.2 项目初始化

```bash
# 后端骨架
cargo new dodogo --bin
cd dodogo
git init
rustup override set stable
cargo add axum tokio serde serde_json sqlx anyhow thiserror
sqlx migrate add init_schema

# 前端骨架（web/ 子目录）
mkdir web
npm init -y
npm i -D esbuild typescript
```

初始化验收：

- `cargo run` 启动后访问 `/healthz` 返回 `ok`；
- `cargo test` 通过（含 1 个冒烟测试）；
- `cargo fmt --check` 与 `cargo clippy -- -D warnings` 零告警；
- Git 首次提交（`MINOR: 初始化项目骨架`）。

## 3.3 代码规范

依据项目《AGENTS.md》要求执行：

1. **KISS**：追求简洁直接，不做无谓抽象；
2. **YAGNI**：只实现当前阶段明确需求；性能缓存等"留到压测再上"；
3. **SOLID**：路由层（handlers）薄、服务层承担业务、repos 管数据；接口按角色拆分；
4. **DRY**：权限判断、校验、错误映射收敛为公共函数；
5. Rust 规范：`rustfmt` 默认风格、Clippy `-D warnings`、错误处理使用 thiserror（库错误）+ anyhow（应用上下文）；
6. 命名：Rust snake_case；前端 TypeScript camelCase；CSS 组件类使用 `block-element`；
7. 注释：只写"为什么"，不写"是什么"；公共接口（API 文档注释）除外；
8. 禁止：`unwrap()` 出现在非测试/非 main 代码（用 `expect` 并注明原因或返回错误）；`unsafe`（除非经过评审）。

## 3.4 Git 提交规范

沿用项目约定，前缀大写，一次提交一个功能：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| FEAT | 新功能 | `FEAT: 卡片拖拽移动接口` |
| FIX | 修复 bug | `FIX: 会话并发失效问题` |
| REFACTOR | 重构 | `REFACTOR: 统一权限校验入口` |
| TYPO | 格式/拼写调整 | `TYPO: 修正模板缩进` |
| MINOR | 杂项 | `MINOR: 更新依赖版本` |
| WIP | 未完成（带序号） | `WIP: 看板拖拽#1` |
| DONE | 最后完成（保留序号） | `DONE: 看板拖拽#3` |

提交要求：

- 原子提交：可编译、可测试、可回滚；
- 消息格式：`前缀: 简要描述（50 字内）`，必要时正文说明背景；
- 功能完成时使用 DONE 收尾，不留 WIP 提交在主干；
- 禁止提交：编译不过的代码、`.env`/密钥、本地调试文件、`target/`、`node_modules/`。

## 3.5 代码审查

- 每次 MR/PR 至少 1 人评审；
- 审查清单：权限校验完整性、事务边界、错误处理、SQL 注入/XSS 风险、性能（N+1、索引）、测试覆盖、命名与规范；
- 合入前必须：CI 通过 + 无高危告警 + 关联需求/缺陷编号。

# 4. P0：工程脚手架与基础架构（约 1 周）

## 4.1 目标

搭建可运行、可测试、可发布的工程骨架，完成技术栈落地验证。

## 4.2 任务清单

- [ ] 初始化 Cargo 工程与目录结构（src/handlers、services、repos、templates、web）；
- [ ] 配置系统：config.toml + 环境变量覆盖 + 默认值；
- [ ] 日志系统（tracing + 文件滚动 + 请求日志中间件）；
- [ ] SQLite 连接池与 PRAGMA 初始化、迁移框架（init_schema 建全表）；
- [ ] 统一错误类型与错误响应中间件；
- [ ] 健康检查 `/healthz`、版本接口；
- [ ] 静态资源服务与 esbuild 构建脚本；
- [ ] 前端骨架：页面母版（顶栏/导航）、登录页静态原型、CSS 变量令牌；
- [ ] CI：GitHub Actions（fmt + clippy + test + build）；
- [ ] 冒烟 E2E：启动→健康检查→打开登录页。

## 4.3 验收标准

- 全表迁移脚本可重复执行（幂等）；
- `cargo run` → `/healthz` 200；
- CI 绿；三平台（win/x64 linux）release 构建成功；
- 登录页按设计令牌渲染，静态资源带 hash 缓存头。

- [ ] Argon2id 注册/登录服务；登录限速与锁定；
- [ ] 会话创建/校验/吊销中间件；Cookie 与 Bearer 双认证；
- [ ] CSRF 双提交令牌中间件；
- [ ] 首次启动初始化向导（创建管理员）；
- [ ] 个人资料：修改昵称/邮箱/密码、上传头像；
- [ ] 会话管理页面（列出/吊销设备）；

# 9. P5：GitLab 联动（约 2-3 周）

## 9.1 目标

实现按任务单号自动关联**私有化部署（自托管）的 GitLab** 提交（GitLab CE/EE 部署于本地网络或自有服务器），支持手动、轮询与 Webhook 三种同步方式。GitLab.com 与 GitHub.com 等公有云平台的联动不在本阶段范围，列入后续版本计划。

## 9.2 任务清单

- [ ] GitLab 配置页（地址、令牌、仓库、匹配正则、同步间隔、自动完成开关）；地址仅接受私有化部署的 GitLab 实例；
- [ ] 配置校验：拒绝 gitlab.com / github.com 等公有云域名并提示"公有云平台支持列入后续版本"；
- [ ] 令牌 AES-GCM 加密存储与主密钥管理；
- [ ] 连接测试（GET /api/v4/user，针对私有化实例）；
- [ ] 增量提交拉取与单号匹配（默认正则 + 可自定义）；
- [ ] 幂等入库 git_commits 与卡片 Git 关联区块展示；
- [ ] Webhook 端点与 X-Gitlab-Token 签名校验；
- [ ] 定时同步后台任务（按项目间隔）；
- [ ] 同步日志与错误提示（令牌失效、仓库无权限、单号不存在）；
- [ ] "Closes #12" 自动完成（可配置）；
- [ ] 匹配预览工具（设置页输入提交消息看匹配结果）。

## 9.3 验收标准

- 提交消息含 `#12` / `DODG-12` 时，卡片 Git 区块出现提交（sha/作者/时间/链接）；
- Webhook 推送后秒级关联；重复推送不产生重复记录；
- 错误签名返回 401；令牌失效时项目设置页明确提示；
- 无卡片对应的单号进入同步日志且不影响其他提交；
- 与私有化部署的 GitLab（本地/自有服务器，或 docker 自建 GitLab CE）完成联调用例 ≥ 10 条；GitLab.com 与 GitHub.com 不在本阶段验收范围。

# 13. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 拖拽与并发冲突复杂度高 | 中 | 高 | P2 预留缓冲周；先做乐观更新再引入冲突处理；E2E 覆盖 |
| GitLab API 版本/权限差异 | 中 | 中 | mock 先行；与真实 GitLab 早联调；令牌最小权限文档化 |

| SQLite 写并发成为瓶颈 | 低 | 中 | WAL+短事务+连接池上限；压测验证；预留 PostgreSQL 切换 |
| SSE 连接与浏览器兼容问题 | 低 | 低 | 心跳+自动重连；降级为轮询开关（配置） |
| 人员/排期不足 | 中 | 中 | 按里程碑裁剪（P3 清单、P4 邮件通知、P5 Webhook 可后置） |
| 安全疏漏（XSS/越权） | 中 | 高 | 权限矩阵自动化用例；安全复核阶段；CSP/白名单默认安全 |
| 数据丢失（升级/误删） | 低 | 高 | 迁移前自动备份；回收站；发布流程强制备份步骤 |

## 可裁剪范围（保底线）

若排期紧张，按以下顺序裁剪（不影响 R1-R8 核心验收）：

1. 邮件通知（保留站内）；
2. Webhook 同步（保留轮询+手动）；
3. 卡片模板、保存筛选视图；
4. 深色模式、多语言英文；
5. 项目回收站降级为"确认后直接删除 + 备份兜底"。

# 14. 发布与运维

## 14.1 发布流程

```text
develop 分支 → 特性分支开发 → MR 合入 develop
  → 每周内部构建（内测） → 验收通过
  → 打 tag v1.0.0 → release 构建（win/linux）
  → 生成安装包与校验和 → 发布说明（含升级与回滚指引）
```

## 14.2 版本号

- `MAJOR.MINOR.PATCH`；破坏性变更 MAJOR，新功能 MINOR，修复 PATCH；
- 升级必须执行：备份 → 替换二进制 → 启动（自动迁移）→ 冒烟（/healthz + 登录 + 打开看板）。

## 14.3 运维手册要点

- 默认监听 127.0.0.1；公网必须反代 + HTTPS；
- 数据目录定期备份（每日自动 + 异地拷贝）；
- 日志滚动策略与磁盘清理；
- 升级回滚：保留上一版本二进制与数据库文件副本。
